1. The big picture

My first attempt to drive a 16-pin HD44780 character LCD from the Raspberry Pi Pico in C: one header file, pico_LCD_display.h, that takes a struct of GPIO numbers and works in 8-bit or 4-bit mode, with or without the read/write pin connected. It was written over three weeks in July 2021, and the same header was copied into my Pico networking experiments in the eater repo, which used the LCD to show each bit as it was sent and received.

The history has two bursts. On 14–15 July the header went from a first upload, to a struct-based API, to supporting a display with RW wired to ground, to 4-bit mode, with a README describing all of it. On 28 July to 2 August it learned to read from the display: the character at the cursor, the whole display memory, and the cursor address. Several commit messages end "-- tested" or "-- not tested", which makes it possible to see which steps were checked on the hardware.

2. How the display is driven

An HD44780 module has 16 pins. Three are control lines, eight are data lines (DB0–DB7), and the rest are power, contrast and backlight. The control lines are:

  • RS (register select): 0 means the byte on the data lines is an instruction (clear, move the cursor, set a mode); 1 means it is data, a character to show.
  • RW (read/write): 0 to write to the display, 1 to read from it.
  • E (enable): the strobe. The display acts on what is on RS, RW and the data lines when E falls from high to low.

So every operation in the header has the same shape, in lcd_set_pins(): set RS and RW, put the byte on the data pins, raise E, wait a microsecond, lower E. Writing "Hello" is five data writes with RS = 1; jumping to a position is one instruction write of 0x80 + address with RS = 0.

The pins are described by a struct, so the caller only has to list GPIO numbers: {RS, RW, E, {DB7, DB6, DB5, DB4, DB3, DB2, DB1, DB0}}. The data array is ordered from DB7 down to DB0, which matters when bits are read back (section 6). An unconnected pin is marked with a sentinel: any value over 30 counts as "not connected", and the README suggests 'n', which is 110 as a number. The RP2040 only has GPIOs 0 to 29, so no real pin can be mistaken for it.

Verified in the code if (display.rw_pin <= 30) decides whether the busy flag can be read, and if any of db_pins[4] to db_pins[7] (DB3–DB0) is over 30, every function switches to 4-bit mode (h_files/pico_LCD_display.h).

3. Initialisation, in 8-bit and 4-bit mode

The display does not know how it is wired, so the header has to tell it, and the datasheet gives a fixed recipe for doing so (the comments cite pages 45 and 46 of the HD44780 datasheet). The 8-bit recipe in lcd_init_display(): wait 45 ms after power-up, send the function-set instruction 0x30 three times with pauses of 5 ms and 120 µs, then 0x38 (8-bit, two lines, 5×8 font). Then display on with cursor (0x0e), entry mode "increment, don't shift" (0x06), and clear (0x01).

4-bit mode uses only DB7–DB4, and each byte goes as two halves (nibbles), high nibble first, each with its own E pulse. The awkward part is the start. At power-up the display is in 8-bit mode and expects a whole byte on every E pulse, with only four data wires connected. So the first instructions are sent as single nibbles with one E pulse each: 0x3 three times, to force a known state, then 0x2, which switches it into 4-bit mode. Only after that can full bytes be sent as nibble pairs, starting with 0x2,0x8 (function set: 4-bit, two lines). That is why the header has a separate lcd_set_pins_4_only() that sends one nibble and one E pulse, used only during initialisation.

Lesson A device that can be wired more than one way has to be told how before it can be talked to normally. The "send 0x3 three times" sequence works whatever state the display was left in, including halfway through a byte in 4-bit mode, which is why datasheets ask for it.

4. Waiting: the busy flag or a fixed delay

Each instruction takes the display some time (most about 40 µs, clear and home much longer). Send the next one too soon and it is lost. There are two ways to wait:

  • Ask the display. With RW connected, read the instruction register (RS = 0, RW = 1): DB7 is the busy flag. lcd_wait_for_busy_flag() switches the DB7 pin to input and pulses E until it reads 0. In 4-bit mode each read is two nibbles, so it pulses E a second time to complete the read, even though only the first nibble holds the flag.
  • Wait long enough. Many modules have RW wired straight to ground to save a pin, so they can never be read. Commit 7862e7f added that case: before each write the header sleeps 50 µs ("37 recomended by datasheet", says the comment), and after a clear it sleeps 2 ms.

Two practical details sit underneath this. The Pico's pins are 3.3 V, while the README wires the module's VDD to 5 V; reading from a 5 V module drives the Pico's pins from the display, which the repo does not discuss (see section 10). And the busy-flag routine saves and restores the state of the RS, RW and data pins around its reads, so it can be called from the middle of a write.

5. Reading back from the display

The second burst added reads. A data read (RS = 1, RW = 1) returns the character at the display's current address, from its DDRAM (display data RAM). The pins have to be switched to inputs before raising E and back to outputs afterwards, and in 4-bit mode the byte arrives as two nibbles from two E pulses.

A read, like a write, moves the address counter on by one. So the final version of lcd_read_current_pos() (ffe1e0a) moves the cursor back one place after reading, to leave it where it was. lcd_read_all_ddram() first reads the current address (an instruction read returns the address counter in its low seven bits), then reads positions 0 to 79 one by one, and finally jumps back to the saved address (2ce12a6, "returns the cursor to origional position").

6. Traps the fixes recorded

Trap: shifting the display instead of the cursor The first lcd_move_one_space() sent 0x18 and 0x1c. In the HD44780's "cursor or display shift" instruction (0001 S/C R/L 00), bit 3 chooses what moves: set, it shifts the whole display; clear, it moves only the cursor. The commit that was marked "-- tested" (63ca12e) changed them to 0x14 (cursor right) and 0x10 (cursor left), the only change between "delete character -- not tested" and "-- tested".
Trap: bits read back in the wrong order The untested read (d835d10) assembled the byte with gpio_get(db_pins[i]) << i. But the pin array runs from DB7 to DB0, so element 0 is the most significant bit and needs shifting by 7, not 0. The tested version (d66d870) uses << (7-i) in 8-bit mode, and 7-i then 3-i for the two nibbles in 4-bit mode.
Trap: a write's middle pulse spoils a read In 4-bit mode a write pulses E between the two nibbles. The read path does its own two pulses, so the same commit (d66d870) limited the write's middle pulse to writes: if ((bit_idx == 4) && (rw == 0)). An extra pulse during a read would consume one nibble of the reply.
Verified by the commit record The steps marked "-- tested" on the hardware: 4-bit read at the cursor (d66d870), reading the whole DDRAM (3a1e30d), and delete character (63ca12e). Marked "-- not tested": the first read code (d835d10) and the first delete (e52460d). The last two commits (2ce12a6, ffe1e0a) carry no mark.

7. General lessons

Say in the commit whether it ran Labelling commits "-- tested" or "-- not tested" cost nothing and is the only reason this page can say which code was proven on hardware. The two traps above are visible exactly because an untested commit was followed by a tested one.
Fall back gracefully on missing wires Treating a missing RW pin or missing DB0–DB3 as configuration rather than a different library meant one header covered four wirings, and each function only had to ask "is this pin connected?".
Array order is a contract Listing pins from DB7 to DB0 is natural for writing (send the top bit first) but means every read has to shift by 7-i. Whichever order is chosen, both directions must agree on it.

9. Test yourself

What do RS, RW and E each do? RS chooses instruction (0) or data (1); RW chooses write (0) or read (1); E is the strobe: the display takes in the data lines when E goes from high to low.
Why does 4-bit initialisation need a function that sends a single nibble with a single E pulse? At power-up the display is in 8-bit mode and takes a whole byte per E pulse, but only DB7–DB4 are wired. So the first instructions (0x3 three times, then 0x2 to select 4-bit mode) must each be one nibble on one pulse. Only then are full bytes sent as two nibbles.
How does the header know a display has its RW pin tied to ground, and what changes? The struct's RW pin is set to a value over 30 (the README suggests 'n', 110). The busy flag can then never be read, so each write waits a fixed 50 µs instead, clear waits 2 ms, and the read functions do nothing.
Why was 0x18 wrong for "move the cursor one place"? In the shift instruction, bit 3 (S/C) set means shift the whole display. Moving only the cursor needs it clear: 0x14 for right, 0x10 for left.
Reading the pins in the order the struct lists them (DB7 first), what shift does element i need? 7 - i: element 0 is DB7, the most significant bit. Shifting by i reverses the byte.
Why does lcd_read_current_pos() move the cursor left after reading? Reading DDRAM moves the address counter on by one, just as writing does. Moving back leaves the cursor where it was before the read.
What does reading with RS = 0 and RW = 1 return? The busy flag in bit 7 and the current address counter in bits 6–0. The header uses it both to wait for the display and to save the cursor position.

10. Open questions found on review

These were noticed while reconstructing this page on 2026-10-06. None was recorded as a problem at the time, and none has been tested.

  • Where does line 2 start? lcd_jump_to_line_2() jumps to address 40 (decimal, 0x28). The eater programs written that same month jump to 0x40 + n for the second line, and in two-line mode the HD44780 maps line 2 to 0x40–0x67. Likewise lcd_read_all_ddram() reads addresses 0–79 as if they were continuous. Try both on the real display.
  • Reading back from a 5 V display. When RW = 1, the display drives the data lines. If the module runs at 5 V (as the README's pin list says), that is 5 V into the Pico's 3.3 V inputs. Measure a data line during a read before relying on it.
  • lcd_return_current_address() does not check whether RW is connected (it writes to the "pin" 'n' if not), and in 4-bit mode it only reads the first nibble, so the low four address bits are lost.
  • Buffer size. lcd_read_all_ddram() writes 80 characters and a terminating zero, so the caller's buffer must hold 81 bytes; the README does not say so.
  • Building it. The repo has no CMakeLists.txt; LCDTest.c needs the Pico SDK and a build file like the ones in eater/network/.

11. Glossary

HD44780
Hitachi's character-LCD controller, copied by most 16×2 and 20×4 text displays. It has an 8-bit or 4-bit parallel interface.
RS, RW, E
The HD44780's register-select, read/write and enable (strobe) lines.
Nibble
Half a byte, four bits. In 4-bit mode each byte is sent as the high nibble then the low nibble.
DDRAM
Display data RAM: the HD44780's memory of the characters on screen, addressed with the "set DDRAM address" instruction (0x80 + address).
Address counter
The HD44780's pointer into DDRAM. It moves on by one after every data read or write.
Busy flag
Bit 7 of an instruction read: 1 while the display is still executing the last instruction.
Sentinel value
A value that cannot be real data, used to mean "not present"; here any pin number over 30.
Pico SDK
Raspberry Pi's C/C++ software development kit for the RP2040 (gpio_init, gpio_put, sleep_us, CMake build).
